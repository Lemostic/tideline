## 一、定位与四条不可动摇的原则

潮线是一款**本地优先、开源免费的多视图看板工具**。数据全部存在本机 SQLite 单文件里，不要求账号、不依赖网络、不收集数据。

所有进入路线图的特性都必须满足三条：

1. **提升个人项目掌控力**，而不是为协作场景增加设置负担；
2. **本地可完整实现**，联网能力必须可关闭、失败可降级；
3. **数据留在本机**，不引入需要上传数据的第三方服务。

外加两条与商业化直接相关、不可动摇的原则：

4. **MIT 许可不变** —— 这是潮线区别于 Vikunja 与 Plane（均为 AGPL-3.0）的核心资产，也是未来做闭源商业客户端与云服务的法律前提；
5. **本地版永远可用且功能不阉割** —— 付费只能收「需要服务器成本」的能力，绝不把本地已有能力挪进付费档换取收入。

已下线的特性：桌面软件使用统计（偏离看板工具定位，后台采样线程已停止，代码与历史数据保留，见调研报告 4.6 节）。

## 二、版本结构与命名规则

路线图分两层：

- **大版本（V1.x / V2.x / V3.x）** —— 一个能力主题的完整战役，跨度若干个小版本。跨大版本允许破坏性调整（数据模型、配置格式、架构），但要提供迁移。
- **小版本（V0.13.0 / V1.2）** —— 一次可独立发布的增量。每个小版本都能独立编译、独立测试、独立使用，不存在「必须等下一个版本才能用」的功能。

命名规则为 `V大版本.小版本.修订`。修订号（第三段）只在同一个小版本需要修补发布时递增，日常功能迭代直接推进小版本号。

**为什么这样拆**：一个大版本塞进十几项功能，会让每个功能都做不透，也失去了「小步验证」的价值。拆成小版本后，每个版本都有可验证的验收标准，用户可以逐个升级，每个版本都能独立拿到收益。

## 三、大版本总览

| 大版本 | 主题 | 一句话定位 | 状态 |
| --- | --- | --- | --- |
| **V0.x** | 本地优先基础建设 | 把单机跑通，架构留口 | 进行中 |

四段之间的关系：**V1.x 决定潮线「像不像一个优秀的本地工具」，V2.x 决定潮线「能不能赚钱」，V3.x 决定潮线「有没有护城河」。** 顺序不可颠倒 —— 本地完整度不达标时上云，只会把不成熟的产品放大；差异化没建立时收费，会把用户推向 Vikunja 与 Notion 免费版。

### 4.1 V0.12.0 多类型任务关系与跨看板依赖（已发布）

**目标**：让任务之间的关联从单一的「前置阻塞」扩展为有语义的关系网，同时打通跨看板的依赖表达。

**交付内容**

- 三种关系类型：`blocks`（前置阻塞，沿用原语义）、`relates`（相关联）、`duplicates`（重复）
- 数据层落地：`card_dependencies` 增加 `relation_type` 列，schema 升至 v15，旧库幂等迁移
- 跨看板依赖放开：不再限制「只能依赖同一看板内的任务」
- 前端：任务详情关系区可按类型添加、切换、移除；卡片与甘特连线区分类型
- 阻塞判定只认 `blocks`：`relates` 与 `duplicates` 不产生阻塞、不参与循环依赖检测
- 备份兼容：旧备份缺少 `relationType` 时按 `blocks` 处理

### 4.2 V0.13.0 自定义字段定义与取值（已发布）

**目标**：让看板能定义自己的字段结构并把值填进任务 —— 这是潮线数据模型从「硬编码」走向「可扩展」的第一步，也是后续筛选视图、报表维度的基础。

**调研依据**：Trello Standard 档把 Custom Fields 列为核心能力；Asana Starter 档同样提供；Notion 的数据库属性是整个产品的地基。三家都把它放在付费档或核心位，说明其价值被市场反复验证。

**交付内容**

- **数据结构**：新增 `custom_fields` 表（`id` / `board_id` / `name` / `field_type` / `options_json` / `sort_order` / `created_at`）与 `card_field_values` 表（`card_id` / `field_id` / `value_text` / `value_number`，主键组合），schema 升至 v16；两张都是新增表，`CREATE TABLE IF NOT EXISTS` 每次开库执行，旧库自动获得
- **两种字段类型**：`select`（单选下拉）与 `number`（数值）。其余类型明确不做，理由见调研报告 4.1.2
- **字段管理入口**：看板「更多操作 → 自定义字段」，可新建、改名、增删选项、调整排序、删除
- **选项管理**：改标签保留原 id，已有任务的值不会失效；删除选项时指向它的取值一并清理
- **取值写入**：任务详情新增「自定义字段」区，单选字段用下拉、数值字段用数字框，改动即时写回本地
- **数据层校验**：字段名同看板唯一；单选至少一个选项、数值字段不许带选项；跨看板赋值、给单选写数字、给数值写文本、非有限数、重复赋值一律拒绝
- **级联清理**：删除字段时连带清理其取值，不留孤儿行；删除任务时同步清理
- **备份往返**：自定义字段与取值随 JSON 备份导出与恢复，旧备份缺少这两项时按空集合处理

**验收标准**

- [x] 可创建「单选下拉」与「数值」两种字段，刷新页面后依然存在
- [x] 字段名在同一看板内唯一，重名有明确提示
- [x] 删除字段后其字段值被彻底清理，数据库无孤儿行
- [x] 选项改名后已有任务仍显示新标签（选项 id 稳定）
- [x] 旧数据库升级到 v16 后原有数据完整无损
- [x] 自定义字段与取值随备份导出与恢复完整往返

### 4.3 V0.13.1 保存的筛选视图与字段筛选联动（已发布）

**目标**：把常用的观察角度固化下来 —— 用户不必每次重新拼装筛选条件。

**交付内容**

- **数据结构**：新增 `saved_views` 表（`id` / `board_id` / `name` / `view_type` / `filters_json` / `sort_json` / `is_builtin` / `created_at` / `updated_at`），schema 升至 v17
- **内置视图**：全部、我的任务、最近更新，不可删除，避免用户把自己锁死
- **字段筛选**：单选字段支持多值或关系，数值字段支持区间
- **关系筛选**：可按「被阻塞」筛选（承接 V0.12 的 `blocks` 判定）
- **交互**：看板头部视图切换条 + 「把当前筛选另存为视图」
- **降级容错**：自定义字段被删除后，引用它的保存视图自动忽略该条件而不是报错

**验收标准**

- [x] 保存的视图在刷新、重启后依然存在
- [x] 切换视图完整还原筛选条件**与排序方式**（只存筛选会造成排序错乱，必须一起存）
- [x] 单选与数值两类字段筛选都生效，且可与现有筛选条件叠加
- [x] 删除字段后相关保存视图不报错、不崩
- [x] 内置视图不可删除

**实现要点**

- 视图按看板隔离，内置视图 id 固定为 `sv_builtin_{看板id}_{all|mine|recent}`，重复补齐不会产生重复行
- 筛选条件与排序方式整体存进 `filters_json` / `sort_json`，字段名统一 camelCase，缺失项补默认值
- 排序键收口成闭集（`due-asc` / `due-desc` / `priority` / `created-asc` / `created-desc` / `updated-desc`），前后端各有一份归一化实现，非法键一律回退默认排序
- 降级规则前后端同源：字段被删 → 丢掉整条条件；选项被删 → 只留还存在的选项；选项被删光 → 整条条件失效
- 浏览器预览模式自带等价实现，内置视图补齐、同名校验、降级规则与桌面端一致

### 4.4 字段值在视图中的展示与批量编辑（待排期）

**目标**：让字段从「配置项 + 抽屉里的一个输入框」变成看板上的常驻信息。

- **视图展示**：表格视图新增字段列；看板卡片把单选字段显示为小色块，数值字段显示数字

**验收标准**

- [ ] 字段值在表格与看板卡片上正确展示，零值与空值可区分
- [ ] 批量编辑可批量设置与批量清空字段值
- [ ] 字段值的展示不拖慢看板渲染（任务量上千时）

## 五、V1.x：单机完整度

V1.x 的目标很具体：**一个优秀的本地看板工具应该有什么，潮线就有什么。** 不涉及任何需要联网或多人协作的能力，因此每一个小版本都可以独立交付、永久免费。

### 5.1 V1.0 自定义字段与筛选视图（正式版）

- **内容**：V0.13.0 / V0.13.1 / V0.13.2 三项能力合并发布为 V1.0 正式版；同时补齐早已存在于数据层的工时字段 UI（`estimatedMinutes` / `actualMinutes`）
- **为什么单独设一个大版本**：自定义字段是数据模型的扩展点，一旦上线就需要长期兼容承诺，值得一个正式版号
- **验收**：三项目标全部达成，工时可在任务抽屉与批量编辑中读写，仪表盘按工时维度可分析

### 5.2 V1.1 里程碑、批量编辑与撤销重做

- **里程碑实体**：可命名、可设目标日期、可关联一组任务；甘特图用真正的菱形标记替代当前的单日降级渲染
- **批量编辑扩展**：标签、截止日期、起始日期加入批量可改范围
- **撤销重做**：覆盖拖拽、批量操作、字段修改等易错操作。回收站只解决「删错了」，不解决「改错了」

### 5.3 V1.2 命令面板与快速捕获

- **命令面板**：复用现有 Ctrl+K 弹窗，支持切换视图、打开页面、新建任务、跳转看板、切换主题，模糊匹配
- **快速捕获**：全局快捷键新建任务，带自然语言日期解析（如「明天下午三点」「下周五」）
- **自动化增量**：补「字段变化」触发与「创建任务」动作，仍不引入通用脚本引擎

### 5.4 V1.3 专注模式与工时自动核算

- **专注模式**：番茄钟 + 绑定当前任务，作为显式开关存在，默认关闭
- **采样恢复**：重新启用 Windows 前台窗口采样（V0.12 已停止线程，表结构与历史数据保留）
- **工时自动核算**：前台应用采样 + 当前活跃任务，推算任务实际投入时间，与手工填写的实际工时对账
- **偏差分析**：计划 vs 实际的对比视图，找出系统性高估或低估的任务类型

### 5.5 V1.4 附件与卡片模板

- **附件**：本地文件复制入库而非引用路径，避免文件被移动后失效
- **卡片模板**：在现有看板级模板之外，增加卡片级模板（标题、描述、标签、字段值的预设组合）
- **折叠列**：长列表折叠，减少看板噪音

### 5.6 V1.5 报表中心与数据导出

- **报表中心**：把现有仪表盘的散点能力收敛成一个页面，支持保存自定义报表切面
- **周期时间**：基于完成时间戳统计，从流出到流入的耗时分布
- **日程负载视图**：按天 / 周呈现任务量与预估工时分布，标出超载区间。**注意**：单人场景下不需要「负责人」字段，负载视图退化为「我」的日程负载即可
- **CSV 导出**：任意视图导出为 CSV，字段值按列导出 —— 这是开源用户的数据可迁移底线

## 六、V2.x：可选云服务层（条件触发）

V2.x 的每一个小版本都带**触发条件**，条件不满足就不启动。这样做是为了避免在还没有付费用户时先背上账号体系与运维负担。

| 小版本 | 内容 | 触发条件 |
| --- | --- | --- |
| V2.0 | 同步协议设计 + 账号体系（只写设计文档与接口定义，不实现） | V1.5 完成且有用户明确提出跨设备需求 |
| V2.1 | 跨设备同步（可选端到端加密） | 有 10 个以上用户明确表示愿意为同步付费 |
| V2.2 | 云备份与分享链接 | V2.1 上线后，备份丢失类反馈持续出现 |
| V2.3 | 团队协作（成员、评论、权限） | 出现真实的 2 人以上团队使用场景（非一人试用） |
| V2.4 | AI 服务（任务摘要、拆解建议） | 有可行的模型成本承担方案（订阅收入覆盖调用成本） |

**硬性约束**：V2.x 不改变本地版的任何能力，也不要求本地版用户注册。所有云能力都是**可选增强**，本地功能永远完整可用。

## 八、商业化路线

### 8.1 三种可选模式与适用条件

| 模式 | 形态 | 适用条件 | 当前判断 |
| --- | --- | --- | --- |
| **本地买断** | 一次付费获得完整本地功能 + 官方签名安装包 + 若干年大版本更新 + 自动更新通道 | 本地功能已足够完整，且希望为「免安装体验 + 官方支持」收费 | 可行，成本最低，随时可开 |
| **云订阅** | 本地版永久免费完整，付费买跨设备同步、团队协作、AI、云备份 | 同步与 AI 的服务器成本可以被订阅覆盖 | V2.x 阶段启用，前提是 V1.x 先做完 |
| **open core** | MIT 社区版功能完整，企业版提供团队管理、自托管运维支持、SSO | 出现真实企业客户 | 暂不启动 |

买断与订阅**可以并存**：买断解决「不想订阅但愿意为本地版付一次钱」的用户，订阅解决「愿意为持续服务付月费」的用户。两者针对的是不同人群，不是二选一。

### 8.2 商业化三条不可逾越的红线

1. **MIT 许可不变。** 一旦改成 AGPL，闭源商业客户端与云服务的路径被直接封死。开源协议的选择只有一次机会。
2. **本地已有能力永不进入付费档。** 例如把表格视图、甘特图、仪表盘设为订阅专享 —— 这会立刻把潮线推进 Notion 免费版与 Vikunja 的对立面，且与「数据留在本机」的价值主张自相矛盾。
3. **不制造锁定。** 任何付费方案都必须提供完整数据导出能力。

另加两条操作层面的禁止：

- **不在没有付费用户规模时先搭账号体系。** 账号、鉴权、密码找回、隐私政策、跨境合规的运维成本远大于早期收益。
- **不用「限时免费」制造虚假紧迫感。** 开源用户对这类套路极其敏感，负面口碑的成本远高于一次促销的收益。

### 8.3 竞品定价对潮线的反向启示

潮线真正争夺的用户不是 Trello Premium 的付费用户，而是：

- **Notion 免费版** —— 不设限的块与数据库，功能广度压制潮线；
- **Vikunja** —— 功能与潮线高度重合，AGPL，自托管，256 MB 内存，部署门槛比潮线还低。

因此潮线的付费点必须建在这两者给不了的东西上：**跨设备的可靠同步、团队协作、本机 AI 能力、以及免部署的官方托管**。

推论很直接：**只做「更多本地功能」无法支撑收费逻辑。** 这是商业化路线必须提前写进路线图的原因 —— 等功能做完再想怎么收费，答案通常会滑向「把已有功能锁起来」，而那恰恰是红线第 2 条禁止的。

### 8.4 触发商业化的三个信号

满足任意一条即启动商业化准备工作，不需要全部满足：

1. **信号一（需求信号）**：持续有用户在 issue 或讨论区问「有没有买断版」「能不能付费支持」。
2. **信号二（成本信号）**：出现潮线本地版无法承担的成本，例如同步服务器、AI 调用。
3. **信号三（生态信号）**：出现愿意为潮线贡献代码或维护的企业 / 团队用户。

在三个信号出现之前，路线图的重心是 V1.x —— 把本地完整度做扎实。

## 九、明确不做清单

| 能力 | 不做的理由 | 是否有例外 |

| 故事点 / 估算点 | 个人任务无此需求 | 无 |

## 十、每个小版本的交付标准

每一个小版本在合并与发布前，必须全部满足：

1. `pnpm typecheck` 无错误；
2. `pnpm test` 全绿（当前 175 项，只增不减）；
3. `cargo test` 全绿（当前 120 项，只增不减）；
4. 生产构建成功（`vite build` + Tauri 打包）；
5. 数据结构变更走幂等迁移，`PRAGMA user_version` 递增，旧库升级后数据无损、旧备份可恢复；
6. 版本号在 package.json、tauri.conf.json、Cargo.toml、Cargo.lock、README 中同步；
7. 产出安装包并记录 SHA256 校验值；
8. 一次提交推送，不把多个小版本混进同一次提交。
