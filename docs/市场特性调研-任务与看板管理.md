## 二、两个市场的能力分层

商用与开源市场在 2026 年已经分化出清晰的形态，不是简单的「功能多少」差异。

**商用侧的核心是「配置深度 + 跨项目聚合」。** Asana 用 Portfolios 把多个项目装进一个鸟瞰视图，用 Workload 回答「这个人的活会不会爆」，用 Goals 把任务进度回写到目标层级，再用 Reporting 出自定义报表。Jira 更进一步，把项目分成 team-managed（看板、状态流转、字段轻量）和 company-managed（工作包、Gantt、成本、工作日志字段）两档，默认强调前者、后者作为可选的严谨模式。monday.com 把重点放在自动化规则和组合视图。Notion 走的是另一条路：数据库引擎提供六种视图和 Rollup，用户自己在上面搭结构。Trello 相对克制，Standard 补齐自定义字段、高级清单和保存搜索，Premium 才放出多视图。

这些能力的共性是**「同一份数据被多个视角反复观察」**——今天按时间轴看排期，明天按负责人看负载，后天按目标看达成率。数据模型是固定的，视角是可换的。

**开源侧的核心是「单机完整度 + 轻量部署」。** 横评给出的判断很直接：Plane 是最均衡的现代全栈，OpenProject 偏正式治理（工作包、Gantt、Scrum、工时、成本、Wiki），Taiga 适合敏捷（Kanban、Scrum、WIP 上限、泳道、Epic），Kanboard 和 WeKan 是轻量派，Vikunja 本质是「以看板为视图之一的个人任务管理器」。许可证层面要注意区分：Plane 社区版 AGPL-3.0，OpenProject 社区版免费但企业功能另售，Planka 仓库自述为 source-available，严格意义上不算开源。

开源项目普遍带有商用产品不会要的东西：Docker 自托管、REST API、Webhook、插件机制、CalDAV 集成、CSV 导入。Vikunja 甚至提供从 Todoist、Trello、Microsoft To-Do 导入任务。

## 三、潮线的能力现状（代码核对结论）

这一节不是照抄 README，而是按 `src/lib/types.ts`、`src-tauri/src/db.rs`、`src-tauri/src/repo.rs` 逐项核对的结果，避免把规划中的功能误记为已有。

| 能力 | 状态 | 依据 |
| --- | --- | --- |
| 看板 / 表格 / 甘特 / 日历四视图 | 已有 | `BoardView = 'board' \| 'table' \| 'gantt' \| 'calendar'` |
| 任务依赖 | 已有，但仅「前置任务」单一类型，且限制同看板 | `repo.rs:1988` 校验 `blocker.board_id != card.board_id` |
| 循环依赖检测 | 已有 | `set_card_dependencies` 校验 |
| WIP 上限 | 已有 | `lists.wip_limit`，超限只警示不阻止 |
| 重复任务 | 已有 | `recurrences` 表，`recurrence_runs` 主键幂等 |
| 自动化规则 | 已有，2 触发 × 5 动作 | `RuleTrigger` 只有 `move_to_list` / `complete` |
| 提醒 | 已有，到期 / 逾期 / 每日摘要 | 走系统通知，按 (kind, day, card_id) 去重 |
| 活动日志 | 已有 | `card_activity` 表，逐字段对比 |
| 目标树 + 进度回写 | 已有 | `goals` / `goal_cards` |
| 看板集（跨看板汇总） | 已有 | `board_sets` |
| 仪表盘 | 已有，含吞吐、年龄、效率、交叉筛选 | `src/lib/dashboard.ts` |
| 使用统计（前台软件时长） | 已有 | `usage_daily` |
| 项目管理（角色/成员/加班/绩效） | 已有 | schema v9–v10 |
| 需求拆解 | 已有，纯本地解析 | `requirementParser.ts` |
| 工时字段 | **数据层已落地，UI 未完成** | `Card.estimatedMinutes` / `actualMinutes`，schema v14 |
| 看板级标签颜色 | 已有（最新提交） | `boards.label_colors`，schema v14 |

据此，真正的空白是：

- **任务关系只有一种语义。** 业界通用的关系模型是多类型的，Jira 默认就带 relates to / duplicates / is duplicated by / blocks / is blocked by / clones 六种。潮线只有「前置」，导致「这两件事相关」「这条重复了那条」这类真实需求无处表达。
- **依赖被锁在单看板内。** 而潮线自己就有「看板集」这个跨看板容器，还具备依赖连线绘制能力，限制在实现上并不必要。
- **没有泳道。** Taiga、WeKan、Jira 都有，看板里横向按负责人/模块分区是很常见的需求。
- **没有自定义字段。** 潮线的数据模型是硬编码的 `priority` + `labels`，Trello Standard 和 Asana 都把它列为核心能力，板栗看板也把它做成付费点。
- **筛选条件不保存。** Trello Standard 的 Saved searches 就是这个，Trello 至今仍把它放在付费档。
- **没有里程碑实体。** 甘特里的「单日里程碑」只是缺日期时的降级渲染，不是可管理的对象。
- **没有附件、没有撤销重做、没有批量编辑覆盖全部字段。**
- **没有命令面板。** 现有搜索是关键词搜索，不是 Linear 那样的命令驱动入口。

## 四、值得吸收的特性与理由

### 4.1 多类型任务关系

**商业依据**：Jira 把问题链接做成六种默认类型并允许管理员自定义；Linear 用 relations 区分 blocking / blocked by / duplicate / related；ONES 的测评把「区分前置、后置、阻塞等类型」列为跨团队依赖建模的首要选型确认点。

**本地可借鉴的部分**：不需要做成管理员可配置的链接类型系统，那对单人工具是负担。只需把现有单一依赖扩展为带类型的边：`blocks`（前置）、`relates`（相关）、`duplicates`（重复）。三种覆盖了绝大多数真实场景，且重复关系有实际用途——潮线的需求拆解已经在做同名检测，说明「识别重复」是真实痛点，现在只能提示跳过，做不成一等公民。

**成本**：schema 加一列 `relation_type`，依赖边表结构小改，前端任务抽屉加一个类型选择器。

**收益**：依赖连线可以从单向箭头扩展为分型连线，仪表盘的「被阻塞」统计也需要按类型区分。

### 4.2 跨看板依赖

**商业依据**：ONES 测评反复强调「确认依赖视图是否支持跨项目」；Jira 的链接类型跨项目可用，路线图能呈现跨项目依赖的传递路径。

**本地可借鉴的部分**：潮线的看板集本来就是跨看板容器，依赖限制在同看板是实现约束而非产品决策。放开后，「A 看板的交付物阻塞 B 看板的任务」这种常见的个人项目结构就能表达。

**风险**：跨看板依赖会让甘特图的依赖绘制变复杂（现有连线基于同看板 DOM 位置计算，跨看板需要另行绘制或降级为不绘制）。建议第一版只做关系数据放开与阻塞判定，连线仍限同看板。

### 4.3 泳道

**商业依据**：Taiga 把 swim lanes 作为敏捷核心能力，WeKan、Jira 都有；Jira 泳道与看板列的组合是其「已配置自动化规则和看板泳道的成熟度团队」这一选型前提。

**本地可借鉴的部分**：潮线的看板列是固定的「待办 / 进行中 / 已完成」，用户若想按负责人、模块、优先级分区，只能靠标签过滤反复切换。泳道能在同一屏内横切显示，适合「一件任务同时属于两个维度」的场景。

**成本**：泳道需要行数据结构（分组键 + 行内列），看板从单层列变成二维布局，是这批建议里工程量最大的一项。分组键可复用现有的 labels 或负责人字段。

### 4.4 自定义字段

**商业依据**：Trello Standard 档明确列出 Custom Fields；Asana 把自定义字段列为核心；板栗看板把自定义字段做成付费能力，之前的对标调研已经把它列为潮线应吸收的方向。

**本地可借鉴的部分**：不做字段类型全家桶（数字、日期、选项、用户……）。个人工具真正会用到的只有两类：**下拉选项**（如「类型：需求/缺陷/运维」）和**数值**（如「影响面：1/2/3」）。潮线现有的 `priority` 恰好就是硬编码的枚举，把它泛化成可配置的选项字段是最自然的路径。

**成本**：需要 schema v15 的 `custom_fields` 表 + `cards.custom_field_values`，字段定义按看板隔离（像现在的 `boards.label_colors` 那样），备份兼容要处理。

**收益**：这是所有建议里解锁能力最多的一个——自定义字段一旦存在，标签、优先级、看板集汇总表、仪表盘交叉筛选的维度都能跟着扩展。

### 4.5 保存的筛选视图

**商业依据**：Trello 把 Saved searches 放在 Standard 档；Notion 的「动态过滤排序」是其数据库引擎的核心卖点；Asana 的 saved views 同理。

**本地可借鉴的部分**：潮线已有相当完整的筛选器（关键词 / 完成状态 / 优先级 / 标签组合，跨四视图生效），但筛选状态是临时的，刷新即丢，也没有入口回到某个常用组合。这对「每天只关心某几个标签的某几个列表」的场景是明确的重复劳动。

**成本**：一张 `saved_views` 表（看板 id、名称、筛选条件 JSON），看板头部加一个下拉切换。

### 4.6 里程碑

**商业依据**：ONES 把「里程碑和迭代节奏」列为跨团队对齐机制；Jira 有版本（Version）作为发布单位。

**本地可借鉴的部分**：潮线有目标树和甘特图，但没有「一个发布/交付节点」的概念。里程碑能让甘特图出现真正的菱形标记而非当前的降级单日渲染，也能给一组任务提供共同的交付期限。潮线现有的「单日里程碑」渲染逻辑可以平滑升级。

### 4.7 番茄钟 / 专注模式

**商业依据**：TickTick 的内置番茄钟是其被选为「视觉规划者」首选的主要原因；个人工具横评把 Pomodoro 列为「专注增强特性」的第一项权重指标。

**本地可借鉴的部分**：潮线已经有 V0.12 的 `estimatedMinutes` / `actualMinutes` 字段和 V0.10 的前台软件使用统计。缺的不是数据，是把二者接起来的那段交互：开始一个任务 → 计时 → 停止 → 实际工时自动回填。这条链路一旦打通，「我到底花了多少时间在这个项目上」才第一次有了真实答案。

**注意**：这是本清单里唯一直接利用潮线独有能力（Windows 前台窗口采样）形成差异化的建议。其它软件能做番茄钟，但只有潮线能同时告诉你「这段时间你在 VS Code 里写了 40 分钟，但这个任务只记了 25 分钟」。

### 4.8 撤销重做

**商业依据**：这是桌面软件的通用预期，Linear 等工具把 Cmd+Z 做得很深；Trello 有 Undo 按钮。

**本地可借鉴的部分**：潮线现在误删任务只能进回收站恢复，误拖动卡片位置或误改优先级没有轻量回退路径。回收站解决的是「删除」，不解决「改错」。

### 4.9 批量编辑的字段覆盖

**商业依据**：所有主流看板都有批量操作；Linear、Asana 的批量编辑可改任意字段。

**本地可借鉴的部分**：潮线现有批量操作覆盖移动列表、设置优先级、标记完成、移入回收站四项。可低成本扩展到标签、截止日期、起始日期。改动集中在已有的批量动作执行路径，收益立竿见影。

### 4.10 命令面板

**商业依据**：Linear 的键盘优先是其口碑来源；Notion 的 Cmd+K 全局搜索是其效率核心。

**本地可借鉴的部分**：潮线已有 Ctrl+K 搜索弹窗和搜索结果直达任务详情，但缺的是「在弹窗里输入命令」的能力——切换视图、打开某页、新建任务、跳转看板、切换主题都能用一条命令完成。这对一个把侧边栏做成十项导航的工具尤其有价值。

## 五、明确不建议吸收的部分

调研中大量出现的热门能力与潮线的定位冲突，不应吸收：

**多人协作全家桶**——成员、评论、@提醒、权限、分享链接、活动流。潮线已在 README 与开发计划中把这定为非目标，理由是这些能力的价值完全建立在「有第二个人在用」之上，单机场景下只会增加设置负担。

**云端同步与账号体系**——直接违背「不用账号、数据只属于你」的产品主张。

**AI 摘要与自动分派**——潮线的需求拆解刻意做成纯本地解析、不经过 AI 服务，这个取舍在本地优先语境下是对的。贸然引入云端 AI 会让「数据不出本机」这句话失效。

**冲刺 / 迭代周期管理**——Cycles、Sprint、Backlog、燃尽图都属于多人节奏的产物。潮线的「我的任务」按截止日期分桶对个人已经够用。

**跨设备移动端**——潮线是 Windows 桌面端，数据模型和前台窗口采样都绑定桌面环境。

## 六、落地建议（与 V0.12 现有规划合并）

V0.12 已经规划了工时、负载视图、报表中心、导出、筛选视图保存。其中「保存筛选视图」与本报告 4.5 重合，可以合并推进。

按「解锁能力 × 实现成本」排序，建议分三档：

**第一档（低成本、高解锁）：**
1. 多类型任务关系（4.1）——在现有依赖结构上加类型，同时解锁重复关系与依赖语义
2. 跨看板依赖放开（4.2）——只放数据层，连线暂不变
3. 保存的筛选视图（4.5）——V0.12 已有规划，合并实现
4. 批量编辑字段扩展（4.9）——复用现有批量执行路径
5. 撤销重做（4.8）——前端栈快照或操作日志

**第二档（中等成本、结构性）：**
6. 自定义字段（4.4）——解锁能力最多，但涉及 schema v15 与备份兼容
7. 里程碑实体（4.6）——甘特图体验的实质升级
8. 命令面板（4.10）——复用现有搜索弹窗

**第三档（高成本、需谨慎评估）：**
9. 泳道（4.3）——看板从一维变二维，工程量最大，建议先做小范围验证
10. 番茄钟 / 专注模式（4.7）——差异化最强，但需要把计时、实际工时、前台应用时长三条线打通，建议在 V0.12 工时 UI 完成后再启动

## 七、需要注意的调研局限

本轮调研以官方功能页、定价页、文档与横评文章交叉核对为主，未逐一深度试用全部产品的付费档位。定价页信息会变动，引用时应以抓取当日的页面为准。Trello / Notion / Asana 等产品的具体功能归属哪个付费档位，本报告只作为「该能力在商用产品中已是标配」的佐证，不构成对潮线定价策略的建议。

开源项目的许可证状态变化较快，其中 Plane 的社区版 / 企业版边界、Planka 的 source-available 标注尤其需要以仓库当前声明为准。
