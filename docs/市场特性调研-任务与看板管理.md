# 任务与看板管理市场特性调研（面向潮线 tideline）

> 调研日期：2026-11-01　文档版本：v2（细化版）
> 调研对象：商业看板与项目管理 SaaS、开源 / 可自托管看板、潮线自身代码库
> 用途：为潮线后续版本提供功能取舍依据，并支撑商业化路线的判断
> 结论先行：潮线的真实对手不是 Trello Premium，而是 Notion 免费版与 Vikunja。功能取舍应以「单机完整度」为主轴；商业化能力必须绑定服务器成本，否则与 MIT 开源 + 本地优先的定位互相拆台。

### 1.3 方法与局限

1. 商用侧采用「官方定价页 + 官方功能页 + 第三方横评」三方交叉；开源侧采用「官方仓库 + 官方文档 + 横评」。
2. 未做深度长期试用，交互层面的优劣以文档描述推断；本文的对比表覆盖「是否具备该能力」，不覆盖「做得好不好」。
3. 潮线现状一节全部来自代码核对，不使用「已有 / 部分 / 规划中」这类模糊描述，只写「有 / 无 / 数据层有 UI 无」三态。
4. 调研范围限定在任务与看板管理方向，不涉及文档协作、即时通讯、代码托管等相邻品类。

## 二、商用市场的能力分层

### 2.1 定价档位对照

**Trello**

| 档位 | 价格 | 该档位新增的关键能力 |
| --- | --- | --- |
| Free | 0 美元 | 最多 10 个看板、无限卡片、基础自动化 |
| Standard | 5 美元 / 用户 / 月 | 无限看板、Custom Fields、Saved searches、Advanced checklists、Card mirroring、List colors、Collapsible lists |
| Premium | 10 美元 / 用户 / 月 | Calendar / Timeline / Table / Dashboard / Map 视图、Workspace 级模板、Collections、Simple data export |
| Enterprise | 17.5 美元 / 用户 / 月 | 组织级管控、SSO |

**Asana**

| 档位 | 价格 | 该档位新增的关键能力 |
| --- | --- | --- |
| Personal | 0 美元 | 最多 2 个用户 |
| Starter | 10.99 美元 / 用户 / 月 | Timeline + Gantt、Reporting dashboards、Unlimited automations、Forms、Custom templates、Custom fields |
| Advanced | 24.99 美元 / 用户 / 月 | Portfolios、Workload、Goals、Rules、跨项目 Dependencies |
| Enterprise | 定制 | SSO、SCIM、审计日志、GA 与支持 SLA |

**其余产品的档位逻辑**

- ClickUp、monday.com：把「自动化规则条数」「视图组合数量」放进付费档，自由版保留核心看板。
- Notion：免费版对个人几乎不设限，付费档买的是「更大用量 + 团队管理 + 权限审计」。
- Linear：免费限 250 个 issue，付费解锁 Projects、Cycles、Insights、SLAs。
- Todoist / TickTick：免费版功能相对完整，订阅主要买跨端同步与高级视图。

**对潮线的三点启示**

1. 自定义字段与保存搜索在商用世界里被放在中档付费位（约 5 美元 / 月），说明它们有真实价值 —— 但也说明用户**不会为单机已有的东西付费**。
2. Notion 免费版的无限制策略把「功能多」这条赛道的价格压到接近零，潮线在功能数量上赢不了，也不该以此为卖点。
3. 真正被付费的是**多端、跨设备、协作、托管** —— 这些恰好是带服务器成本的部分，天然可收费。

### 2.2 协作型产品的能力骨架

Asana 与 Jira 的骨架高度相似：

- **Portfolios / Portfolio**：把多个项目装进一个鸟瞰视图，回答「整体进度如何」。
- **Workload**：按人分配任务量，回答「这个人的活会不会爆」。
- **Goals**：把任务进度回写到目标层级，回答「做这些是为了什么」。
- **Reporting**：自定义报表，回答「我想看哪个切面」。
- **Timeline / Gantt**：排期与依赖，回答「什么时候能做完」。

Jira 最有价值的不是功能本身，而是**两档项目模式**：

- **team-managed**：状态流转 + 看板 + 少量字段，敏捷团队开箱即用；
- **company-managed**：工作包、WBS、Gantt、成本、工时日志字段齐全，适合正式治理。

同一套数据模型，按需开启严谨度；默认给轻的，严谨的那套作为可选升级。

**潮线可借鉴的部分**：不引入「项目模式」这种重概念，但借鉴其思路 —— 基础能力永远免费可用，高阶能力（跨看板汇总、里程碑、报表中心）以「可选开启」的形式提供，而不是「换一个版本才能用」的形式。这个区别在商业化阶段极其重要，见第六节。

### 2.3 轻量型 / 个人型工具对照

| 产品 | 核心差异点 | 潮线是否覆盖 |
| --- | --- | --- |
| Todoist | 自然语言快速录入、Karma 积分激励 | 部分：有搜索无快速捕获 |
| TickTick | 内置番茄钟 + 日历双向订阅 + 习惯打卡 | 无 |
| OmniFocus | 透视（Perspective）自定义分组、action / forecast 分流 | 无 |
| Things 3 | Inbox / Today / Upcoming / Areas 四层 + 标签着色 | 部分：有看板无 Inbox 层 |
| Akiflow | 时间线 + 跨应用任务合并 | 无 |
| Motion | AI 自动排程（按优先级与截止自动排进日程） | 无 |

这一层的产品几乎没有「项目管理」概念，它们的竞争维度是**输入效率 + 今日视图 + 不遗漏**。潮线目前强在结构化看板与报表，弱在**输入效率**：没有快速捕获、没有命令面板、没有自然语言日期解析（现有的需求拆解解析器只服务于需求文档，不服务于日常录入）。

## 三、开源市场的能力分层

### 3.1 八个项目对照

| 项目 | 许可证 | 定位 | 强项 | 短板 |
| --- | --- | --- | --- | --- |
| Vikunja | AGPL-3.0 | 个人任务 + 看板多视图 | 单二进制 Go、内存低、CalDAV、任务关系、重复任务、多视图、导入导出 | 协作弱、UI 偏旧、AGPL 对闭源商业化不友好 |
| Plane | AGPL-3.0 | 现代全栈项目管理 | 视觉现代、Cycles / Modules / Views 完整、Issue 属性丰富、社区活跃（6 万余 star） | 部署重（2 GB 内存起）、AGPL、社区版有功能边界 |
| OpenProject | GPL-3.0 | 正式治理 | 工作包、WBS、成本、工时、Wiki、季度规划 | 学习曲线陡、功能为组织而生 |
| Taiga | AGPL-3.0 | 敏捷 | Scrum + Kanban、WIP 上限、泳道、Epic | 配置繁琐、UI 偏重 |
| Focalboard | MIT | 极简看板 | 极轻、MIT 许可、与 Mattermost 集成 | 无任务层级、无报表、无关系 |
| Kanboard | MIT | 极简看板 | 插件生态、自动触发器 | 数据模型极简、视图单一 |
| Wekan | MIT | 看板 | 看板 + 规则 + 附件 + 通知成熟 | 聚合弱、代码库老旧 |
| Leantime | AGPL-3.0 | 项目交付 | 目标-战略-战术分层、Checklist、阶段推进 | 结构较固定 |

### 3.2 开源同业的七项共性能力

REST API、Webhook、附件、CSV / JSON 导入导出、CalDAV 订阅、Docker 自托管、插件机制。

这七项是开源项目区别于「纯本地小工具」的标配。潮线目前的对应情况：备份导入导出已有（可视为 JSON 导出的加强版），其余缺失。

### 3.3 三点参考价值

1. **AGPL 是开源项目商业化的主要障碍。** Vikunja 与 Plane 都因此把「官方云托管」当作主要收入来源。潮线选择 **MIT 许可**，这在法律上保留了未来做闭源商业客户端与云服务的空间 —— 这是潮线目前最被低估的战略资产，必须写进路线图。
2. **轻量是开源工具的生存线。** Vikunja 256 MB 对 Plane 2 GB，用户用安装门槛投票。潮线的单文件 SQLite + 免安装应当作为核心宣传点，而不是技术细节。
3. **数据可迁移是开源用户的底线预期。** 任何第三方工具都应能读潮线的数据，不能因为格式封闭而被用户抛弃。

#### 4.1.2 自定义字段类型对照

| 类型 | Trello | Asana | Notion | 潮线决策 |
| --- | --- | --- | --- | --- |
| 单选下拉 | 有 | 有 | 有 | **做** |
| 多选下拉 | 无 | 有 | 有 | 不做（标签已覆盖） |
| 数字 | 有 | 有 | 有 | **做** |
| 日期 | 有 | 有 | 有 | 不做（已有起止日期） |
| 勾选 / 复选 | 无 | 有 | 有 | 不做（子任务已覆盖） |
| 人员 | 无 | 有 | 有 | 不做（单人本地） |
| 网址 | 无 | 有 | 有 | 不做（描述可写） |
| 附件 | 无 | 有 | 有 | 随附件能力排期 |
| 关联 / 关系 | 无 | 有 | 有 | 不做（任务关系已覆盖） |
| 公式 | 无 | 无 | 有 | 不做 |
| 汇总 Rollup | 无 | 无 | 有 | 不做 |
| 按钮 | 无 | 无 | 有 | 不做 |

九类主流类型里，潮线只做 **单选下拉 + 数字** 两类。理由：

- 覆盖个人场景中绝大多数真实诉求 —— 优先级变体（单选）、状态细分（单选）、评分（数字）、预估量级（数字）；
- 两类都不需要公式引擎与关系推导，实现成本与查询成本最低；
- 两类都能被 SQLite 索引直接过滤，不需要把表达式求值塞进查询路径。

后续若用户确有诉求，可在 V1.x 评估增加「日期」与「文本」两类，但**不在 V1.0 之前加**。

#### 4.1.3 字段值存储方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 方案 1 | `cards` 表加一个 JSON 列 | 改动最小，备份天然兼容 | 无法建索引，筛选排序只能应用层全量过滤；选项合法性无法约束 |
| 方案 2 | 独立关联表 `custom_fields` + `card_field_values` | 可建索引、可 SQL 筛选排序、选项可约束、可外键级联删除 | 多两张表，读写需 join |
| 方案 3 | 每种字段类型一张表 | 约束最强 | 类型演进时表数量膨胀，迁移复杂 |

**决策：方案 2。** 理由是自定义字段的核心价值就是「按字段值筛选与排序」，方案 1 在任务量上千后必然退化，而潮线的数据模型已经明确要支持「同一组数据多个视角反复观察」。

拟定表结构：

- `custom_fields(id, board_id, name, field_type, options_json, sort_order, created_at)` —— `options_json` 存 `[{ id, label, color }]`，选项 id 稳定不随改名变化；
- `card_field_values(card_id, field_id, value_text, value_number)` —— 主键 `(card_id, field_id)`；`value_text` 存选项 id，`value_number` 存数值。

### 4.2.3 保存视图的设计要点

- 保存内容必须**同时包含筛选条件 + 排序方式 + 视图类型**，只存筛选会造成「切回来发现排序变了」的困惑；
- 作用域是**看板级** —— 跨看板保存视图价值低，看板集层面的共享视图可另议；
- 名称在看板内唯一；
- 内置视图（全部 / 我的任务 / 最近更新）不可删除，避免用户把自己锁死；
- 支持「把当前筛选条件另存为新视图」这一最常见路径。

### 4.6 时间与专注：潮线唯一具备结构性优势的地方

现状：V0.10 曾实现 Windows 前台窗口采样（`usage_daily` 表），V0.12 随「使用统计」下线停止采样线程，表结构与历史数据保留。

**三个机会点**

1. **任务实际工时自动核算** —— 前台应用采样 + 当前活跃任务，可推算某任务的实际投入时间，与手工填写的 `actualMinutes` 对账；
2. **计划 vs 实际偏差** —— 用 `estimatedMinutes` 与自动核算时间对比，找出系统性的高估或低估，让估算校准成为可能；
3. **软件切换次数** —— 切换频率是上下文切换成本的可观测代理指标，Everything 2.0 之类的工具靠这个思路活了下来。

前提：需要用户显式重新开启使用统计（作为 V1.3「专注模式」下的开关，而非全局默认开启）。

## 六、商业模式调研

### 6.1 十一个产品的收费模式

| Trello | 订阅 | 5 / 10 / 17.5 美元 每用户月 | 限 10 看板，功能很少 |

| Jira | 订阅 | 免费（10 用户）+ 7 美元起 | 免费档对团队够用 |

另外 Vikunja 的云托管版为 4 欧元 / 月个人版 —— **它正是开源 AGPL 项目最典型的变现形态**。

### 6.2 三条可行路径

**路径 A：本地买断**

- 形态：一次付费获得完整本地功能 + 若干年的大版本更新 + 官方签名安装包 + 自动更新通道。
- 依据：Things 3、OmniFocus、Sublime Text 等一批独立开发者产品。
- 优点：与 MIT 开源定位不冲突（源码仍公开，买断的是签名包、构建服务与官方支持）；用户预期清晰；几乎没有服务器成本。
- 风险：一次性收入，需要持续发版维持说服力；没有经常性收入支撑长期投入。

**路径 B：云订阅**

- 形态：本地版永久免费完整 + 付费云服务（跨设备同步、团队协作、AI 服务、云端备份与分享）。
- 依据：Vikunja、Plane、Notion、Trello。
- 优点：收入可持续，可承载持续产生的服务器成本；天然把「有成本的能力」放进付费档。
- 风险：一旦引入账号体系，就带来隐私承诺、运维负担、故障面与信任损耗 —— 与「数据在本机」这一核心卖点正面冲突。

**路径 C：open core（社区版 + 企业版）**

- 形态：MIT 社区版保持功能完整，企业版提供团队管理、自托管运维支持、SSO 等。
- 依据：Plane、OpenProject、Focalboard。
- 优点：不牺牲开源完整性，企业客户买单点明确。

**结论：A 与 B 可以并存，C 只在真正出现企业客户时才需要。** 早期不选 C，因为没有企业客户时 C 只是增加维护面。

### 6.3 对潮线的四条必须坚持

1. **MIT 许可不变。** 这是潮线区别于 Vikunja 与 Plane（均 AGPL-3.0）的核心资产，也是未来做闭源商业客户端与云服务的法律前提。开源协议一旦从 MIT 改成 AGPL，商业化路径会被直接封死。
2. **本地版永远可用，且功能不阉割。** 付费能力只能是需要服务器成本的能力；绝不把本地已有能力挪进付费档换取收入。
3. **不要求账号即可完成全部本地工作。** 从首次使用到卸载，全程不需要注册。
4. **数据永远可导出。** 任何付费方案都必须提供完整导出能力，不制造锁定。

### 6.4 潮线不能做的三件事

- **不能把本地已有能力放进付费档。** 例如把表格视图或甘特图设为订阅专享 —— 这与第 2 条直接冲突，也会立刻失去开源用户信任。
- **不能在还没有付费用户规模时先搭账号体系。** 账号、鉴权、邮件找回、隐私政策、跨境合规的运维成本远大于早期收益。
- **不能用「限时免费」制造虚假紧迫感。** 开源用户对这类套路极其敏感，负面口碑的成本远高于一次促销的收益。

### 6.5 竞品定价的反向启示：潮线的真正对手

真正与潮线争夺同一批用户的，不是 Trello Premium，而是：

- **Notion 免费版** —— 不设限的块与数据库，功能广度压制潮线；
- **Vikunja** —— 功能与潮线高度重合，AGPL，自托管，256 MB 内存，部署门槛比潮线还低。

因此潮线的付费点必须建在这两者给不了的东西上：**跨设备的可靠同步、团队协作、本机 AI 能力、以及免部署的官方托管**。

反过来说，只做「更多本地功能」的版本无法支撑收费逻辑 —— 这正是商业化路线必须提前写进 roadmap、而不是等做完了再想的原因。

## 八、结论与对路线图的导向

**三个市场判断**

1. **功能维度**，潮线的空白集中在三处：**字段体系**（自定义字段 + 保存视图）、**效率入口**（快速捕获 + 命令面板）、**时间感知**（专注与工时核算）。这三处恰好构成 V1.x 的骨架。
2. **商业化维度**，本地功能越完整越难收费 —— 这不是矛盾，而是结论。收费必须落在服务器成本上，因此路线图必须是「单机完整度先行、可选云服务层后置」的两段式结构。
3. **差异化维度**，潮线的机会在**本机感知**：能同时知道「你在哪个软件里待了多久」「这个任务记了多少工时」「计划与实际差多少」的本地工具，目前市面上没有。这是 V3.x 的主题。

**对路线图的三条直接要求**

- 版本必须拆成「大版本 + 小版本」两层，小版本可独立发布、独立验证，避免一个大版本塞进十几项功能；
- 商业化路线必须与大版本结构对应写清楚，明确哪些能力永远免费、哪些能力要等服务器；
- 每一项进入路线图的能力都要能回答「它让潮线更接近哪种不可替代性」，而不是「竞品有所以我们也要有」。
